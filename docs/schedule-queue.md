# 持久化调度队列

`SparkTask` 是业务目标状态，`ScheduleJob` 是持久化同步意图、版本、删除标记、重试时间和租约，`ScheduledTask` 是执行入口投影，`TaskSchedule` 是最近一次同步状态。任务创建、编辑和启停将业务变更与入队放在同一短事务中，事务提交后才调用调度平台。其他旧批量写入路径的崩溃间隙由核对扫描恢复。

任务准入的最终额度和四分钟间隔检查也在该事务中进行。全局时段使用额度策略单例行作为 PostgreSQL 锁，顺序为策略 → 队列任务 → 业务任务。SQLite 不支持行级 `SELECT FOR UPDATE`，任务、队列和执行权写事务先对策略行做不改变值的 UPDATE 获取写锁，避免多个进程从读取升级到写入时失败。可用时间查询只是提示，保存时重新检查；管理员变更额度后的自动暂停规则仍由额度服务负责。

每个任务一次只允许一个未过期租约，默认两分钟。远程调用在事务外；完成时检查租约令牌和版本，旧结果不能发布新的成功状态。失败保留执行关闭状态，30 秒起指数退避，最多 15 分钟；手动同步可立即入队。已成功任务每十分钟重新核对并提交当前目标状态。worker 重启不丢重试记录。

远程平台没有比较版本后写入的机制：租约不能阻止暂停进程恢复后产生迟到的云端写入。发现迟到完成时会关闭执行投影并立即重新核对；无法获知的迟到写入依靠周期核对最终修复。因此这是最终收敛，不是跨数据库和云服务的强一致事务。执行入口另有当前启停、当前计划时间和一次性执行权检查，队列重试不会重发聊天消息。

删除先暂停并记录不可撤销的删除意图。删除成功后保留队列墓碑，周期清理迟到生成的同名触发器。墓碑不能在旧 worker 仍可能恢复时清除；当前未设置自动过期，会产生持续的云 API 核对请求。重新创建任务使用新 ID。

## 运行

先在目标数据库、原加密密钥环境下运行 `python -m core.db`。

- 常驻环境：运行 `python -m core.task.schedule_worker`，每 15 秒检查待处理项，每轮最多处理 20 项。进程应交由部署环境的进程管理器维护。
- 定时运行：同样环境运行 `python -m core.task.schedule_worker --once`。
- Serverless：外部定时器可用服务令牌调用 `POST /api/internal/schedules/reconcile`，每次最多处理 10 项。必须限制访问并配置请求时限；当前补偿扫描仍会检查全部业务任务，大规模部署需进一步分页。

API 请求仍会尝试立即同步一次，保持原页面交互。**仅发布 API 并不意味着后台重试已在运行**；需要上述一个持续唤醒入口。不使用 FastAPI 临时后台任务承担持久化工作。不能在测试环境指向生产数据库启动 worker。

当前测试用临时 SQLite、真实 API 和模拟云端传输，覆盖：其他数据库写入不被远程请求阻塞、两个独立 Python 进程的领取排他、版本过期、租约过期及旧结果迟到、取消后恢复、退避重试、业务写入后未入队、删除失败后重试。PostgreSQL 和实际云调用按本次要求未验证。
